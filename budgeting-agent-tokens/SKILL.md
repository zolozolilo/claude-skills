# Экономия токенов при работе с агентами

## Суть

Каждый шаг агента заново читает весь накопленный контекст. Расход ≈ шаги × размер контекста, поэтому длинный агент дорожает как квадрат. В замере одного дня агенты дали ~90 % расхода; один агент (941 шаг, контекст до 967 тыс.) съел четверть дня, потому что ему досылали доработки.

**Порог: 300 тыс. токенов контекста агента.** Выше — записка передачи и свежий агент. Порог держит хук (`hooks/`).

## Правила

1. **Один агент — одна короткая задача**, чтобы уложиться в ~300 тыс.: код с тестами — одна задача; полный прогон, браузерные пробы, сборка — отдельные.
2. **Доработка после сдачи.** Сначала замер (ниже). Контекст агента меньше 300 тыс. и правка мелкая — SendMessage ему. Больше — новый агент: задание + записка передачи, старого не продолжать.
3. **В каждом задании:** «после каждого этапа — коммит и обновление записки `<scratchpad>/handoff/<ветка>.md`». Любого агента можно остановить и продолжить свежим без потерь.
4. **Ждать одной командой.** Очередь или долгий прогон — один вызов Bash с циклом ожидания внутри (timeout до 600000), а не десятки коротких проверок: каждая перечитывает весь контекст. Дольше 10 минут — `run_in_background` и ждать уведомления. Агент не пишет промежуточных «жду».
5. **Мои ответы.** В точке остановки (после релиза) — записать состояние и предложить пользователю `/compact <что сохранить>`; набирает только он.
6. **Большие выводы** — в файл, читать хвост или Grep; большие логи — сжимать (например, инструментом сжатия контекста, если установлен).
7. **Модели и число агентов:** Sonnet по умолчанию, Opus — сложное и ревью, Haiku — поиск и сверка; не больше 2–3 одновременно.
8. **Задание точное:** файлы и функции, где читать, команда проверки, что считать «готово». Агент не ищет сам — поиск съедает шаги. Агент-разведчик без права записи вернёт весь результат отчётом в мой контекст; если нужен результат-файл — давать агента с правом записи.
9. **Проверка сданной работы** — git (коммит, чисто, версия) и хвост лога тестов; прогоны агента не повторять. **Тесты в два уровня:** агент гоняет только тесты своего участка и одну пробу (минуты); полный прогон — один раз перед релизом. Тесты, закрепляющие точный текст или строку кода, — долг: переписывать на проверку смысла, когда агент их всё равно трогает.
10. **Мои вызовы:** независимые — одним сообщением; файлы — offset/limit/Grep; скиллы — только нужные шагу.
11. **Ответ пользователю** — 3–6 строк: итог, цифры, что нужно от него; таблица — по просьбе. Вопросы — только когда без ответа нельзя идти дальше.
12. **Документы — после дела, не вместо.** Решение принято → сразу задания; планы короткие (≤ 300 строк), подробности живут в задании агента.
13. **Направление сменилось — остановить агентов, чья работа устарела**, не дожидаясь отчёта.
14. **Тяжёлые прогоны** на одной машине — в одну очередь; браузерные пробы параллельно дают ложные тайм-ауты: не больше 2–3 агентов с тяжёлыми прогонами. Срок пользователю — с запасом на очередь.
15. **Агенту про процессы:** в «НЕЛЬЗЯ» каждого задания — «останавливать только по своим PID; kill/pkill/taskkill по шаблону и имени — нет» (однажды агент убил все `pytest` на машине).

## Протокол общения с агентами

Язык — телеграфный: поля, цифры, пути; без вежливости, без пересказа задания, без кода в отчёте. Пользователю так не пишу — ему понятным языком.

**Задание (≤25 строк):**
```
ЗАДАЧА: <одна строка>
ГДЕ: <папка/ветка>, от <коммит>
ФАЙЛЫ: <файл:функция>, …
ЧИТАТЬ: <заметка / раздел> (больше ничего не исследовать)
НЕЛЬЗЯ: <прод, push, секреты, …>
ПРОЦЕССЫ: только по своим PID; kill/pkill/taskkill по шаблону или имени — нет
ПРОВЕРКА: тесты участка — свои новые + те, где есть изменённые функции (grep -l); одна проба; ПОЛНЫЙ прогон агенту не давать
КРАСНЫЙ ДО КОДА: новый тест сначала падает на старом коде — 2–3 строки FAIL в записку ДО правки (без этого лист не принимается)
ГОТОВО, КОГДА: <критерии>
ЭТАПЫ: после каждого — коммит + <scratchpad>/handoff/<ветка>.md
СТИЛЬ: между вызовами инструментов не пиши пояснений; мне — только ОТЧЁТ по форме, ≤8 строк.
```

**Отчёт агента:**
```
ИТОГ: готово | частично | стоп
КОММИТ: <hash> <ветка>; копия чистая: да/нет; ВЕРСИЯ: <…>
ТЕСТЫ: <команда> → <N ok / M fail>; лог <путь>
НЕ СДЕЛАНО: <пункты | нет>
ВОПРОС: <один, с рекомендацией | нет>
```

Отчёт попадает в мой контекст и перечитывается каждым моим ответом: отчёт на 3 тыс. × 100 ответов = 300 тыс. Короткий отчёт — прямая экономия.

## Метрика

**Токенов на релиз** = расход дня (скрипт) / число релизов за день. Записывать после каждого релиза и сравнивать: цель — каждый релиз дешевле прошлого.

## Замер

```bash
PYTHONUTF8=1 python ~/.claude/skills/budgeting-agent-tokens/scripts/tokens_today.py [--date ГГГГ-ММ-ДД] [--session ID]
```

Показывает расход за день: мои ответы, агенты, самые дорогие агенты с числом шагов и контекстом на последнем шаге (пометка «больше 300 тыс.»). Запускать перед доработкой агента (правило 2), после релиза и раз в день; называть цифры, а не ощущения. Скрипт ищет журналы в `~/.claude/projects/`.

## Хук бюджета

`hooks/agent_budget_hook.py` — PreToolUse/PostToolUse хук: в подагенте предупреждает с 250 тыс. контекста, с 290 тыс. запрещает всё, кроме записки передачи, git-коммита и сдачи отчёта; запрещает Read длинного файла без `limit`; ловит одну и ту же Bash-команду 3 раза подряд. В главной сессии молчит. Пороги — `hooks/agent_budget.json`. Подключение — в README.

## Записка передачи

```markdown
# <задача> — ветка <имя>, последний коммит <hash>
Сделано: <пункты с коммитами>
Осталось: <пункты>
Проверки: <что прогнано, итог, путь к логу>
Решения и подводные камни: <что важно не повторить>
Продолжить с: <первая команда или шаг>
```

## Красные флаги

| Мысль | На деле |
|---|---|
| «Агент уже в теме, быстрее дослать ему» | Каждый его шаг читает 500+ тыс.; свежий агент с запиской дешевле в разы |
| «Это одна мелкая правка» | Мелкие правки копятся — так и вышли 941 шаг |
| «Пусть проверяет очередь каждую минуту» | Каждая проверка — весь контекст заново; ждать одной командой |
| «Сэкономили, наверное, много» | Замер скриптом, потом цифры |
